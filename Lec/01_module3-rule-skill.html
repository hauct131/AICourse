Module 03 · Code Assist

Dùng AI (Claude Code) để xây dựng ứng dụng

Ở Module ② bạn đã học model chạy thế nào. Bây giờ ta dùng model đó để viết phần mềm. Claude Code là một agent chạy trong terminal: nó đọc codebase, lập kế hoạch, sửa nhiều file, chạy test và tự sửa lỗi. Nhưng có một sự thật cốt lõi phải hiểu trước: mỗi phiên (session) của AI là một tờ giấy trắng — nó không nhớ gì về project của bạn. Đó là lý do vì sao ta cần Rules, Skills và một hệ thống quản lý tri thức.

Vòng lặp làm việc của một coding agent

Claude Code không "đoán một phát ra code". Nó chạy một vòng lặp giống một kỹ sư thật: quan sát → lập kế hoạch → sửa → chạy → kiểm chứng, lặp lại đến khi đạt.

→
🧭

Chia nhỏ nhiệm vụ, quyết định sửa file nào
→

Vấn đề "mất trí nhớ" (session amnesia): Mỗi lần bạn mở một phiên mới, agent không nhớ quy ước code của bạn, những gì đã sửa hôm qua, hay bài học đã rút ra. Nếu không có gì "dạy lại" nó mỗi phiên, nó sẽ lặp lại lỗi cũ và làm sai chuẩn của project.

Bấm thử: cùng một yêu cầu, có luật vs không có luật

Yêu cầu: "Thêm một API endpoint mới"
Agent đoán theo thói quen chung: đặt tên file tùy ý, dùng thư viện nó thích, bỏ qua quy ước migration SQL của bạn, không viết test theo chuẩn project. Kết quả "chạy được" nhưng lệch chuẩn — bạn phải sửa lại tay.

3 công cụ để "dạy" agent hiểu project của bạn

📜
Rules (luật)
Ràng buộc luôn bật. Mọi phiên đều phải tuân. Ví dụ: "migration SQL phải đăng ký trong MIGRATIONS".
🧩
Skills (năng lực)
Quy trình gọi theo yêu cầu. Chỉ nạp khi cần. Ví dụ: skill "tạo báo cáo PDF".
🗂️
Tri thức (md files)
Ghi lại điều đã tìm ra & bài học, có cấu trúc để sau này nạp vào RAG (Module ④).
Ba tab tiếp theo đi sâu vào từng công cụ, và tab ⑤ là Lab — bạn tự viết một Rule và một Skill đơn giản. Đây là nền tảng cho Module 4 (RAG): tri thức bạn ghi hôm nay chính là dữ liệu bạn nhúng vào RAG buổi sau.
Module 03 · Rules

Rules — bộ luật mà mọi phiên phải học

Rule là ràng buộc luôn bật: những quy ước không được vi phạm, được nạp vào đầu mỗi phiên để agent "hiểu cách làm việc trong project này". Trong Claude Code, luật sống ở các file Markdown mà agent đọc tự động: CLAUDE.md, must-read.md, và thư mục .claude/rules/.

Agent nạp luật như thế nào?

🚀
Mở phiên
Claude Code khởi động trong thư mục project
→
📖
CLAUDE.md
File đầu tiên agent đọc — chỉ mục & luật cốt lõi
→
🔑
must-read.md
File "chìa khoá" — luật bắt buộc của project
→
📂
.claude/rules/
Các luật chi tiết theo chủ đề
must-read.md là chìa khoá. Đây là file mà mọi phiên đều phải học đầu tiên để biết cách làm việc với project: quy ước CSS, cách đồng bộ prompt agent với DB, mẫu migration SQL, cách đặt tên file Q&A... Ai (hoặc AI nào) mới vào project chỉ cần đọc file này là biết luật chơi.

Giải phẫu một Rule

Một rule tốt rất cụ thể: nêu điều phải/không được làm, kèm lý do và ví dụ. Dưới đây là một rule thật (rút gọn) từ một project automation testing:

.claude/rules/file-organization.mdRULE · luôn bật
# Quy tắc tổ chức file

## Rule B — File Q&A: `rag-ai-local/QandA/MMDDYYYY_<Chủ_Đề>.md`
- Mỗi chủ đề một file, tên có ngày + chủ đề (KHÔNG cần chữ "QandA").
- Câu hỏi đánh số `Q1`, `Q2`, ... trong từng file.
- Ví dụ: `07042026_Agentic_Crawler_Replay_Trap.md`

## Rule C — File .md khác: `rag-ai-local/functionality-docs/MMDDYYYY/NN_<slug>.md`
- Chỉ có thư mục ngày MMDDYYYY — KHÔNG có thư mục tính năng.
  File có tiền tố `NN_`, slug chứa tên tính năng.
- Ví dụ: `07042026/01_thiet-ke-corrector-agents.md`
Đồng bộ bắt buộc: khi sửa một rule ở .claude/rules/, phải cập nhật bản sao tương ứng trong must-read.md (và ngược lại). Luật mà "hai nơi nói khác nhau" thì agent sẽ làm sai — giữ một nguồn sự thật.

Rule tốt vs Rule dở

✅
Cụ thể, kiểm chứng được
"Mọi file migration SQL mới phải đăng ký trong danh sách MIGRATIONS ở config/migrations.py, theo đúng thứ tự chạy." → Agent biết chính xác phải làm gì.
⚠️
Mơ hồ, vô dụng
"Viết code sạch và tuân theo best practice." → Không đo được, mỗi phiên hiểu một kiểu. Agent không thể tuân một luật không cụ thể.
Nguyên tắc vàng khi viết Rule: nếu bạn không thể chỉ ra một ví dụ đúng và một ví dụ sai cho luật đó, thì luật còn quá mơ hồ. Viết lại cho tới khi cụ thể và kiểm chứng được.
Module 03 · Skills

Skills — năng lực gọi theo yêu cầu

Nếu Rule là "luật luôn bật", thì Skill là một quy trình đóng gói sẵn mà agent chỉ nạp khi cần. Nó dạy agent cách làm một việc cụ thể — ví dụ "tạo file PDF", "review code theo checklist", "khởi động stack sạch". Skill được viết trong một file SKILL.md và được kích hoạt khi bạn gõ tên nó (dạng /tên-skill) hoặc khi nhiệm vụ khớp mô tả của skill.

Rule khác Skill như thế nào?

Tiêu chí📜 Rule🧩 Skill
Khi nào hoạt độngLuôn bật mọi phiên, mọi tác vụTheo yêu cầu — chỉ khi gọi/khớp
Bản chấtRàng buộc, điều được/không được làmQuy trình, các bước để làm một việc
Kích hoạtTự động nạp vào ngữ cảnhGõ /slug hoặc khớp mô tả tác vụ
Ví dụ"Không hardcode màu hex trong CSS""Tạo báo cáo PDF từ dữ liệu"
Chi phí ngữ cảnhLuôn tốn token (nên viết ngắn gọn)Chỉ tốn khi được nạp
Ẩn dụ dễ nhớ: Rule là nội quy công ty dán trên tường — ai vào cũng phải theo. Skill là cuốn cẩm nang quy trình trên kệ — khi cần làm việc gì mới lấy đúng cuốn đó ra đọc.

Cấu trúc một file SKILL.md

Một skill gồm frontmatter (metadata ở đầu file, giữa hai dấu ---) để agent biết khi nào dùng, và phần thân là hướng dẫn từng bước.

.claude/skills/clean-restart/SKILL.mdSKILL · theo yêu cầu
---
name: clean-restart
description: Khởi động lại stack sạch: xoá container + image API,
  rồi build lại. Dùng khi cần chạy code mới nhất trong Docker.
---

# Clean Restart

Khi người dùng yêu cầu "khởi động lại sạch", làm theo các bước:

1. Xoá CHỈ container + image của API (KHÔNG đụng vào DB pgvector).
2. Build lại: `docker compose up -d --build automation-test-api`.
3. Đợi health-check `GET /docs` trả 200 rồi báo người dùng.

Lưu ý: tuyệt đối không xoá volume database — mất toàn bộ dữ liệu crawl.

Bấm thử: điều gì kích hoạt một Skill?

Kết quả
Người dùng gõ đúng tên skill → agent nạp SKILL.md và làm theo 3 bước trong đó. Đây là cách gọi tường minh nhất.
Mô tả (description) quyết định độ chính xác kích hoạt. Viết description rõ ràng, nêu đúng tình huống dùng — nếu quá chung chung, agent sẽ nạp skill sai lúc, hoặc bỏ sót khi đáng dùng.
Module 03 · Quản lý tri thức

Quá nhiều file .md — quản lý sao cho nạp được vào RAG

Khi làm việc với AI, bạn sẽ sinh ra rất nhiều file .md: ghi chú điều tra, thiết kế, bài học rút ra, hỏi–đáp... Nếu vứt lộn xộn thì vô dụng. Bí quyết: ghi chúng theo một quy ước cố định, chia làm hai loại — functionality/ (tri thức theo tính năng) và QandA/ (hỏi–đáp) — để sau này cắt nhỏ (chunk) và nhúng vào RAG (Module ④).

Hai loại tri thức, hai thư mục

🧠
rag-ai-local/functionality-docs/
Tri thức về một tính năng: nó hoạt động ra sao, quyết định thiết kế, bài học, hậu quả. Sau này hỏi RAG "tính năng X làm gì?" → lấy ra đúng ghi chú này.
💬
rag-ai-local/QandA/
Các cặp câu hỏi – câu trả lời, mỗi file một chủ đề, tên MMDDYYYY_<Chủ_Đề>.md. Định dạng Q/A rất hợp với RAG: hỏi một câu là lấy được câu trả lời tương ứng.

Cây thư mục theo quy ước

project/ ├── must-read.md # chìa khoá — luật bắt buộc, mọi phiên đọc đầu tiên ├── CLAUDE.md # chỉ mục & luật cốt lõi (init) ├── .claude/rules/ # các Rule chi tiết (luôn bật) ├── .claude/skills/ # các Skill (theo yêu cầu) └── rag-ai-local/ # ⭐ MỌI tri thức .md nằm ở đây — sẵn sàng cho RAG ├── QandA/ # tên = MMDDYYYY_<Chủ_Đề>.md (KHÔNG cần chữ "QandA") │ ├── 07042026_Agentic_Crawler_Replay_Trap.md │ └── 07072026_Rule_Skill_Basics.md └── functionality-docs/ # CHỈ có thư mục ngày MMDDYYYY (KHÔNG có thư mục tính năng) └── 07072026/ ├── 01_thiet-ke-corrector-agents.md # NN_ + slug chứa tên tính năng └── 02_handoff-fixing-test-runner.md
Quy tắc vàng: KHÔNG để file .md tri thức nào ở thư mục gốc hay nơi khác — mọi tài liệu vào rag-ai-local/functionality-docs/, mọi hỏi–đáp vào rag-ai-local/QandA/. Ngoại lệ duy nhất: file rule, skill, init (must-read.md, CLAUDE.md, .claude/...). Nhờ gom một chỗ, cả kho tri thức sẵn sàng để chunk + nhúng RAG.
Vì sao đặt tên theo ngày & số thứ tự? Vì nó cho mỗi mẩu tri thức một "địa chỉ" ổn định, không trùng, và giữ đúng thứ tự thời gian. Khi chunk để nhúng RAG, mỗi file là một đơn vị gọn — metadata (ngày, tính năng, số thứ tự) trở thành nhãn để lọc/truy hồi.

Metadata — để file sẵn sàng cho RAG + Elasticsearch

Cả hai loại — QandA và functionality — dùng CHUNG một header metadata + TL;DR (chỉ khác trường type), để chunk & index đồng nhất. Chỉ đặt tên đúng thôi chưa đủ: mỗi file phải mở đầu bằng metadata (YAML frontmatter) và một khối TL;DR. Vì sao? Vì khi nhúng vào pgvector, các trường metadata trở thành cột để lọc trước (pre-filter) — thu hẹp phạm vi trước khi so khớp vector (nhanh & chính xác hơn). Còn title + TL;DR được index cho Elasticsearch (full-text / BM25) — tức hybrid search: vừa tìm theo nghĩa (vector) vừa tìm theo từ khoá.

rag-ai-local/QandA/07042026_Agentic_Crawler_Replay_Trap.mdmetadata bắt buộc
---
title: Agentic Crawler Replay Trap       # tiêu đề — cũng để full-text
date: 2026-07-04                     # lọc theo khoảng thời gian
type: qanda                          # qanda | functionality
area: agentic-crawler               # lọc theo tính năng (facet)
status: implementation-complete       # in-progress | investigation | ...
session_id: 912b894b-7508-4bb3

- Where: observer._compute_state_hash + navigator.
- Impact: Sửa hash một nguồn → crawler qua được mọi bước.

Pre-filter + Hybrid search: retriever chạy 2 tầng — (1) lọc theo metadata (area='agentic-crawler' AND status='implementation-complete') để loại bớt, rồi (2) tìm trên vector và full-text (Elasticsearch) trong phần còn lại. Bấm thử: hỏi một câu, RAG lấy đúng file nào?

RAG truy hồi

Module 03 · Lab thực hành

Lab: Viết Rule & Skill đầu tiên của bạn

Mục tiêu: trên project lab_01-Hello-World, bạn sẽ (1) viết một Rule đơn giản, (2) viết một Skill đơn giản, và (3) ghi lại một mẩu tri thức theo quy ước QandA/ + functionality/. Đây là hành trang cho Module ④ (RAG).

Chuẩn bị: mở terminal tại thư mục lab_01-Hello-World, chạy claude để vào Claude Code. Yêu cầu: đã cài Claude Code, có Docker (từ Module ②).

Phần 1 — Viết một Rule luôn bật

1

Tạo file luật

Tạo .claude/rules/coding-convention.md với một luật cụ thể, kiểm chứng được:

.claude/rules/coding-convention.mdbạn viết
# Quy ước code — Lab Hello World

## Rule 1 — Mọi hàm Python phải có type hints
- Tham số và giá trị trả về đều phải khai báo kiểu.
- Đúng:  `def greet(name: str) -> str:`
- Sai:   `def greet(name):`

## Rule 2 — Không print() trong code chính, dùng logging
- Dùng `logging.info(...)`, không dùng `print(...)` ngoài file test.
2

Đăng ký luật để agent chắc chắn đọc

Thêm một dòng trỏ tới rule trong CLAUDE.md (tạo file nếu chưa có):

CLAUDE.mdbạn viết
# CLAUDE.md

## Luật project
- Xem [.claude/rules/coding-convention.md] — type hints & logging (bắt buộc).
3

Kiểm chứng luật hoạt động

Trong Claude Code, yêu cầu agent viết một hàm mới. Nó phải tự động tuân luật (có type hints, dùng logging):

claude — lab_01-Hello-World
> Viết hàm add_numbers cộng hai số trong app.py ● Đã đọc .claude/rules/coding-convention.md ● Viết app.py: def add_numbers(a: int, b: int) -> int: # ✔ có type hints logging.info("adding %s + %s", a, b) # ✔ dùng logging, không print return a + b

Phần 2 — Viết một Skill theo yêu cầu

4

Tạo file SKILL.md

Tạo .claude/skills/run-hello/SKILL.md — một quy trình chạy & kiểm tra app:

.claude/skills/run-hello/SKILL.mdbạn viết
---
name: run-hello
description: Build & chạy app Hello World bằng Docker rồi kiểm tra
  output. Dùng khi cần chạy thử app sau khi sửa code.
---

# Run Hello

1. Build image: `docker build -t hello .`
2. Chạy container: `docker run --rm hello`
3. Kiểm tra output có chuỗi `Hello`; nếu không, báo lỗi kèm log.
5

Gọi skill

Gõ /run-hello trong Claude Code. Agent nạp SKILL.md và làm theo 3 bước — bạn không phải nhắc lại quy trình mỗi lần.

claude
> /run-hello ● docker build -t hello . → OK ● docker run --rm hello → "Hello, World!" ● Output chứa "Hello" ✔ — app chạy đúng

Phần 3 — Ghi tri thức cho RAG Module ④

6

Ghi một cặp Q&A theo quy ước (kèm metadata)

Tạo rag-ai-local/QandA/07072026_Rule_Skill_Basics.md — tên = ngày + chủ đề, mở đầu bằng frontmatter + TL;DR:

rag-ai-local/QandA/07072026_Rule_Skill_Basics.mdbạn viết
---
title: Rule & Skill Basics
date: 2026-07-07
type: qanda
area: rules-and-skills
status: implementation-complete
tags: [rule, skill, logging]
---

## TL;DR
- What: Phân biệt Rule vs Skill & quy ước logging trong Lab.

## Q1: Rule và Skill khác nhau chỗ nào?
Rule luôn bật (ràng buộc mọi phiên); Skill nạp theo yêu cầu.

## Q2: Vì sao dùng logging thay cho print?
Logging điều chỉnh được mức độ, ghi ra file, không làm bẩn output.
7

Ghi một ghi chú functionality (cùng metadata header)

Tạo rag-ai-local/functionality-docs/07072026/01_lab-notes-rules-and-skills.md — chỉ có thư mục ngày, slug chứa tên tính năng. File functionality dùng y hệt frontmatter + TL;DR như file QandA — chỉ khác type: functionality. Nhờ vậy cả hai loại chunk & index giống nhau.
